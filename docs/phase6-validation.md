# Phase 6: authorized hybrid search

The user authorized Phase 6 on 20 October 2026. This phase adds text queries across the existing local multimodal index, filters, evidence grouping and an interface that opens immutable citations. Completion on the CPU-only laptop is recorded in the acceptance report, `evaluation/reports/phase6-completion.json`; real-model development checks are in `phase6-corpus.json` and `phase6-calibration.json` in that directory. Phase 7 release benchmarks remain a separate task.

## Search behavior

Refresh the app and use **Search your sources**. Describe a passage, visual event or sound, or enter a literal filename/identifier. Source and file-type selectors are always visible. More filters exposes representation, language, all-required tags, UTC dates and media intervals. **Open evidence** restores the existing document/image or media viewer at the matching region or interval. Nearby evidence is separately labelled and does not contribute ranking votes. Citation links retain the exact revision and segment set. More from this file repeats the query within that asset.

Text snippets are rendered as literal text and labelled extracted text, OCR or ASR. Native image, visual and sound matches can have no text; the interface asks the user to inspect the evidence rather than supplying a quotation. Recognition warnings and authorized processing counts are available with the search details. There is no generated answer or captioning dependency.

`POST /api/workspaces/{w}/search` uses the frozen Pydantic request/response contracts. The request contains the workspace selector, text, filters, result count and optional experiment mode. Responses record the same request ID as the HTTP trace header, pinned generation/profile, retrieval configuration and SHA-256, filters, branch ranks/scores, citations, bounded context and stage timings. Scores are ranking signals. `GET .../search/facets` returns only authorized published source/type counts and workspace index readiness. There is no shared query or content cache.

## Ranking and adopted decisions

The `retrieval` module separates request contracts, SQL scope/candidate retrieval, grouping/fusion and HTTP orchestration. Existing preprocessing, embedding publication and evidence resolution retain their own modules.

Every branch uses the same current source RLS, complete generation membership, asset tombstone checks and filters before limiting candidates. The query pins one active generation/profile before inference and embeds once. PostgreSQL exact cosine returns up to 150 segments, with the maximum compatible vector score for a split segment. PostgreSQL FTS uses stored language configuration and `websearch_to_tsquery`/`ts_rank_cd` for up to 150 text candidates. Literal case-insensitive substring lookup supplies up to 50 additional candidates, preserving punctuation in filenames/identifiers; `%` and `_` have literal substring meaning.

Exact cosine is the adopted local search baseline for the current 197-vector corpus. Phase 5's profile-specific physical HNSW index remains intact and its administrative ANN diagnostic remains available. User search does not currently choose ANN. Filtered ANN recall, its activation threshold and larger-corpus latency belong to Phase 7 measurements. Each retrieval SQL statement has an eight-second deadline; this is containment, not an end-to-end latency guarantee.

Grouping precedes RRF. Segments must share an asset/revision and have temporal/text interval or page-region IoU of at least 0.5. Text spans must share a text artifact; page regions must share a page. Missing page boxes merge only an identical anchor. Each group is compared to its deterministic representative, preventing transitive overlap chains from absorbing an entire timeline. A branch gives a group one vote at its best compacted group rank, regardless of repeated candidates, vector splits or representations. Dense, FTS and identifier branches have equal weights with RRF constant 60. Context contributes no votes. The first ten results have at most three groups per asset; a single-asset filter bypasses that cap. No text reranker discards native matches.

The experiment option `strategy=per_modality` reserves 38/38/37/37 dense candidates for document/image/video/audio, with the same 150-candidate total ceiling. Empty slices do not donate their budgets. Both strategies use the same storage and exact cosine scores. Modes `hybrid`, `dense`, `lexical` (including identifiers) and `derived_dense` support later controlled evaluation. They are API experiment options, not extra product controls. Physical modality-specific indexes remain deferred.

## Filters and access

Within each list, values use OR; distinct filters use AND. Tags require every supplied tag. Dates are half-open `[after,before)`: source-created and source-modified refer to connector metadata on the asset; ingested refers to the published immutable revision's import time. Missing dates fail an active date filter. Language filters match segment metadata, with `und` for unknown. Existing inputs normally record `en` only for OCR/ASR; language detection is not added. Media intervals match overlapping original-time anchors with exclusive ends. Non-temporal evidence does not match an interval filter.

Source/asset selectors cannot confer access. Candidate SQL, facets, neighboring evidence, processing counts and final materialization use the runtime database role and forced RLS. After model inference membership is checked again; after ranking candidates are re-read and ranks are recomputed when their visible set changes. Final result/context membership is checked before serialization, and citations/playback separately reauthorize every request. Historical citations remain usable under the existing retention/access rules. Already delivered client bytes cannot be revoked.

Processing counts cover authorized, nondeleted assets under source, asset, file-type and tag filters. They include unpublished files, pending desired revisions and current processing errors. They deliberately omit segment/language/time/date predicates because unfinished inputs may not have those fields yet; the UI explains this scope. Counts contain no private-source inventory. Tags can be filtered when present in stored metadata; this phase does not add a tag editor.

Adopted limits are 2,000 query characters, 1–30 result groups, at most 50 source IDs, 50 asset IDs, four modality values, six representation values, 20 language values and 20 tags. Each group exposes at most eight matching citations and two same-set/same-representation neighbors. Neighbor expansion preserves the requested filters. Model-token admission remains Phase 5's pinned processor policy; an oversized query fails rather than splitting/truncating.

The CPU advisory gate remains shared with ingestion/indexing. Search attempts it without waiting: a busy heavy producer returns an explicit retryable 503. A running request keeps the gate until inference completes. This bounds laptop contention but does not promise concurrent search/ingestion latency. The private model queue retains its query priority; scheduling is non-preemptive. The model remains CPU FP32 and no GPU is used.

## Relevance policy

Dense-only evidence requires cosine at least 0.70; a lexical or literal-identifier match can independently qualify. `phase6-calibration.json` records four synthetic/public positive development queries and six deliberately unrelated queries against the retained corpus. Positive maximum scores ranged from 0.725 to 0.824; negative maxima ranged from 0.603 to 0.680. This showed why the initial 0.30 policy was unsuitable. The fixed 0.70 threshold separates this small development sample. Dense candidates below it cast no fusion vote and cannot replace independently qualifying lexical evidence. It is versioned in the retrieval configuration.

These examples are not independent test labels or a calibrated probability model. Broad false-useful-evidence and answerable-rejection rates, hard negatives, modality-specific thresholds and sensitivity to new uploads remain Phase 7 work. The interface returns **No useful evidence found** when no group passes the current policy, including when filters remove all candidates. Adding a new corpus can change the score distributions.

## Validation and reproduction

Run `python3 scripts/dev.py verify` against the running stack, `pnpm --dir frontend build`, then `backend/.venv/bin/python scripts/check_search_evidence.py`. Run the real-model checker as a single interactive client, separately from browser search/heavy ingestion; the deliberate CPU-busy response is not a successful search. The checker verifies retained original checksums, both candidate strategies, native silent-video and non-speech audio filters, transcript/OCR retrieval, source scopes and every returned citation/context locator and viewer descriptor. Its query timings include ordinary development conditions and are not a latency SLA benchmark.

Integration tests use the real restricted PostgreSQL role and server-validated fixture sessions. In-process API tests substitute fixed query vectors to make filter/ranking/failure assertions deterministic; real model coverage is measured separately by the retained-corpus checker. Tests include generation cutover during inference, source-grant revocation during inference and ranking, source/asset guessing, context bounds, date/tag/language/representation intersections, model-budget rejection, CPU-busy behavior, missing text on native audio, tombstones, branch/group deduplication and diversity. The existing connector, extraction, media, publication, crash/restart and RLS suite remains part of the release run.

Browser evidence covers audio search to native playback, visual search to a timed video result and document/image citation opening. Screenshots and final measured counts are listed in the completion report. Historical Phase 2–5 reports are preserved. This phase changes no originals, embedding profiles, generation publication rules or database migrations.

## Completed local measurements

The final full suite passed **188 tests in 151.01 seconds**, with one upstream Starlette/httpx TestClient deprecation warning. Strict TypeScript and the Vite production build passed. All 46 retained originals passed checksum verification. Eight real-model positive runs (four queries in each strategy) found an expected fixture in their first ten groups. Six development negatives abstained. Five source-filter checks preserved scope, and four additional checks retrieved native silent video, non-speech audio, ASR and OCR. In total, 64 matching/context citations and 34 viewer descriptors resolved correctly. These are smoke checks, not a frozen gold benchmark.

The active generation still contains 197 vectors and 46 published assets. Migration head remains `0018_embedding_invariants`; queries ran as `videomind_app`. The nine-service stack used about 4.33 GiB in one post-validation idle snapshot with the CPU model loaded. This does not measure peak inference memory or concurrent throughput. Real-model query timings are retained in the corpus report; no p95/p99 claim is made. Browser media elements reached ready state 4 with the expected three-second audio and four-second silent-video durations. The scanned document displayed its selected OCR region, and the 451×300 original image reopened through its stable citation.
