# Action-aware video retrieval: bounded CPU-first options

Research date: **20 October 2026**. Status: **proposal, not an adopted model or serving change**. No model was downloaded, installed or benchmarked for this note. The core remains the pinned `google/embeddinggemma-2` checkpoint. See [the measured Phase 7 failures](../phase7-validation.md) before interpreting this research as a recommendation to deploy.

## What the present model supplies

The [pinned Google model card](https://huggingface.co/google/embeddinggemma-2/blob/914f7f89142e33e77833254d9c9b90c3cef7303b/README.md) describes a shared 768-dimensional embedding for text, images, video and audio, with an 8,192-token context. Video is sampled through the vision encoder; the documented default is one frame per second. Its output represents the input as a whole. The card describes retrieval and classification uses, but does not specify an action-onset/offset output or a calibrated probability that an action occurred. It identifies context complexity and training-data coverage as limitations. It licenses the checkpoint under Apache 2.0 and recommends FP32 on CPUs without native BF16 support.

The [Transformers processor documentation](https://huggingface.co/docs/transformers/model_doc/embedding_gemma2) separately documents a default 32-frame cap, uniform overflow sampling and omitted timestamps. These defaults are not the same thing as the model's theoretical token limit. VideoMind explicitly supplies its own ordered frames with processor resampling disabled and timestamps omitted; see [runtime adapter](../../backend/src/videomind/embeddings/runtime.py) and [profile definition](../../backend/src/videomind/embeddings/profile.py). Any sampling, image-token-budget or timestamp experiment must record the effective processor configuration and a distinct representation recipe. Enabling timestamps is a hypothesis to test, not an action-localization fix established by the documentation.

Local evidence already argues against a blanket FPS increase: the four-asset, four-second Phase 7 diagnostic changed the fight-positive cosine from 0.6265 at 1 fps to 0.6292 at 4 fps while serial experiment time rose from about 105 to 439 seconds. It was oracle-localized and small; it establishes neither general action accuracy nor a complete temporal search comparison.

## Distinguish the tasks

An ordinary fixed-class action classifier answers which of its trained labels best describes a clip. It cannot acquire an arbitrary new action merely because a user types one. A video/text model can compare clips with novel text descriptions, but open vocabulary does not guarantee recognition of every action. Neither a clip label nor a clip/text similarity identifies exact event boundaries. These are interface distinctions for the proposed design, not claims of measured VideoMind accuracy.

Temporal localization requires separate evidence: action start/end annotations, candidate intervals and evaluation of their overlap. Scene cuts, optical flow and person motion can propose intervals; none establishes that the motion is a fall or a fight. Preserve their output as proposals, not verified action labels. A pose or classification score is also not interchangeable with a cosine score or a calibrated user-facing probability.

## Optional candidates worth one bounded experiment

| Candidate | Useful role | Main limit and selection risk |
| --- | --- | --- |
| **MediaPipe Pose Landmarker**, one pinned task bundle | Offline posture/movement features and proposed fall intervals for sufficiently visible people. Test full-frame detection first; person crops/tracking would be additional independently evaluated components. | Does not output fall/fight labels or open-vocabulary embeddings. Small overhead people, occlusion and interacting people are expected failure risks to measure. Pose dropout must abstain rather than imply no event. |
| **Microsoft X-CLIP**, initially `microsoft/xclip-base-patch32` as an offline comparison | A candidate video/text relevance signal with explicit cross-frame processing; compare action phrases and hard negatives against the current native embedding. | Another model/runtime/profile and inference cost. Clip scoring is not boundary prediction. Kinetics-trained benchmark accuracy does not establish fall/fight accuracy on these CCTV cameras. |

**Pose evidence and licensing.** Google's [Python guide](https://developers.google.com/edge/mediapipe/solutions/vision/pose_landmarker/python) documents image/video operation, 33 landmarks with visibility information, configurable pose count, and tracking that can reduce repeated detection. Offline video calls block and accept frame timestamps. VideoMind should supply retained PTS-derived times rather than copying the guide's nominal-FPS example. The [upstream CPU graphs](https://github.com/google-ai-edge/mediapipe/blob/master/mediapipe/modules/pose_landmark/README.md) explicitly support CPU inference. The [Python implementation](https://github.com/google-ai-edge/mediapipe/blob/master/mediapipe/tasks/python/vision/pose_landmarker.py) carries Apache 2.0. That code license alone is insufficient evidence for every downloadable bundle: archive the exact task-bundle license/notice and hash before adoption. CPU support establishes an available execution path, not its memory, speed or accuracy on this laptop; these remain unmeasured.

**X-CLIP evidence and licensing.** Microsoft's [official project](https://github.com/microsoft/VideoX/tree/master/X-CLIP) and [implementation](https://github.com/microsoft/VideoX/blob/master/X-CLIP/models/xclip.py) implement cross-frame communication, temporal integration and video/text scores; the loader has a CPU FP32 path. The [publisher-hosted checkpoint](https://huggingface.co/microsoft/xclip-base-patch32) identifies an eight-frame, 224-by-224 Kinetics-400 model and MIT licensing; its card explicitly says Hugging Face authored that card. The [repository license](https://github.com/microsoft/VideoX/blob/master/LICENSE) is MIT. Pin an immutable checkpoint/source revision and verify all artifact terms before adoption. The CPU branch does not validate CPU end-to-end usability. Peak resident memory, decoding cost, wall time per video minute, query cost and coexistence with the existing encoder are unknown. Do not confuse this Microsoft X-CLIP with another research project sharing that name.

## Recommended selection sequence

1. **Establish labels and the candidate-recall baseline first.** Review fall onset/impact/recovery, fighting intervals, and hard negatives such as sitting, bending, lying down, close conversation and walking. Keep clip identity out of model input: filenames, attribution headings and publisher labels must not become visual evidence. Include untrimmed clips with repeated events and no-event intervals.
2. **Separate admission from recognition.** In the demonstrated UR Fall case, the positive already reaches the raw candidate list and is removed by final acceptance. Evaluate lower intermediate video floors and fixed candidate budgets offline, keeping final acceptance separately calibrated. A later reranker cannot recover a positive discarded before it runs. Measure candidate Recall@K separately from accepted-result precision/recall. Select thresholds on development families and lock them before evaluating held-out families.
3. **Test temporal proposals with the existing encoder.** Compare bounded overlapping windows, recording original PTS, sampling count, window length/stride, crop and token budget. Do not repeat the same dense-FPS experiment and present it as a new motion model. Use uniform proposals as a fallback: proposal-only gating must not discard low-motion or occluded falls.
4. **Run one optional branch at a time.** Pose is a narrow movement-feature experiment; X-CLIP is the open-vocabulary comparison. Keep both offline and serial at first. Neither becomes a second always-loaded service or an extra synchronous search dependency without resource and latency evidence.
5. **Promote only a measured winner.** Compare to the frozen baseline using action-family Recall@10/nDCG, hard-negative false acceptance, temporal Recall@10 at IoU 0.3/0.5/0.7, boundary errors and valid original-media citations. Report per-camera/person-size slices, failed requests, bootstrap uncertainty and all resource costs. A known-example success is a regression check, not held-out validation.

No new checkpoint's vectors may be compared directly with EmbeddingGemma vectors. If a second model wins, its separate profile supplies a separately calibrated score or ranked candidate branch; fusion must be evaluated. Any predicted interval keeps producer/profile identity and its original-time mapping. Attribution-to-video navigation may help users browse, but must remain distinct from a visual scene match.

The existing two-CPU/6.5-GiB encoder envelope and shared admission gate remain constraints, not newly granted capacity. Record fresh process-cold and warm timings, per-run peak memory, vector/storage growth and search contention before deployment. Stop an experiment that exceeds its agreed bound. Optional model feasibility and dataset-transfer quality remain open until measured; this note does not waive the original Phase 7 release criteria or require a GPU.
